# my-claude-harness

Claude Code（Anthropic の CLI コーディングエージェント）の、**自分が実際に毎日使っている
設定一式**。汎用フレームワークではなく、1人の作業環境をそのまま置いたもの。
そのままフォークして自分の環境に持っていける形にしてある。

やっていることは Anthropic が公開している使い方をほぼそのままなぞっている。

- 探索 → 計画 → 実装 → 検証 → コミット の順に進める
- 恒久的なルールは `CLAUDE.md` に置いて毎セッション固定する
- 「書いた本人とは別の文脈が検証する」分離を入れる
- **組み込みで足りるものは作らない**

なので追加しているのはサブエージェント3つとスキル5つだけで、
残りは組み込みの `/code-review` `/run` `/goal` `/run-skill-generator` を使っている。

Claude Code 2.1.261 で動作確認している。

## 構成

```
CLAUDE.md     全プロジェクト共通のルール
agents/       サブエージェント定義
skills/       スラッシュコマンド
install.sh    ~/.claude へ1ファイルずつリンクを張る
```

**このリポジトリがマスター**で、`~/.claude` 側はシンボリックリンク。
ここを編集すれば全プロジェクトに即反映される。

## 導入

置き場所はどこでもよい。以下は `~/p-dev/my-claude-harness` に置いた場合。

```sh
git clone <このリポジトリ> ~/p-dev/my-claude-harness
cd ~/p-dev/my-claude-harness
```

### 1. 環境依存の1行を書き換える

このリポジトリで環境に依存するのは、ドキュメントの保管先1つだけ。
`skills/doc-storage/SKILL.md` の中の次の行を自分の環境に合わせる。

```
DOC_STORAGE_ROOT=~/dev/doc-storage
```

他のファイルはこのパスを持たず、`skill: doc-storage` を参照している。
書き換えるのはここだけでよい。ディレクトリ自体は先に作っておく。

### 2. リンクを張る

```sh
./install.sh
```

`~/.claude/{agents,skills}` に1ファイルずつリンクが張られ、`~/.claude/CLAUDE.md` も
このリポジトリを指す。

> **注意**: `~/.claude` に同名のファイルがあれば `<名前>.bak.<日時>` に退避されたうえで
> リンクに置き換わる。消しはしないが、自分の設定が入っているなら中身を確認してから
> 実行すること。同名でないファイルには触れない。

> **リポジトリを移動したら `./install.sh` を再実行する。** リンクは絶対パスなので、
> 移動しただけで全部切れてハーネスが丸ごと無効になる。エラーは出ず、
> ただ効かなくなるだけなので気付きにくい。

### 3. settings.json に手で足す

`settings.json` はリンクしない（Claude Code 自身が書き換えるため）。
`~/.claude/settings.json` に以下を含める。`~` は展開されないので絶対パスで書く。
`install.sh` が実際に書くべき値を最後に表示するので、それを貼ればよい。

```json
{
  "permissions": {
    "additionalDirectories": ["/Users/<you>/dev/doc-storage"]
  },
  "env": {
    "CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS": "4",
    "CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH": "2",
    "CLAUDE_CODE_GOAL_CHECKIN_MINUTES": "0"
  }
}
```

`additionalDirectories` は doc-storage への書き込みを許可するため。
`env` の上2つは委譲の上限（既定は同時20）。プロンプトで念押しせず、
ここで決定的に止める。3つ目は `/goal` がアイドル中に自分からターンを
開始してフルコンテキストを送るのを止める。

### 4. プロジェクトごとに1回だけ

```
cd /path/to/your-project
claude
> /run-skill-generator     # ビルド・起動の手順を .claude/skills/run-*/ に記録
> /doc-init                # doc-storage に枠を作る
```

**`/run-skill-generator` が肝。** ビルド・起動の手順が `.claude/skills/run-<名前>/`
に記録され、以降 `/run` と全エージェントがそれに従う。これが無いとエージェントが
自走できない。

ドキュメントをリポジトリ内で管理するプロジェクトなら `/doc-init` は不要。
ドキュメント機能自体が要らないなら、`doc-writer` / `/doc` / `/doc-init` を消して
`CLAUDE.md` のドキュメント節を削れば、残りはそのまま動く。

## サブエージェント

| エージェント | モデル | effort | 役割 |
|---|---|---|---|
| `plan-reviewer` | Fable | xhigh | 実装プランの批評。実装はしない |
| `test-runner` | Sonnet | high | テストの作成・実行・切り分け |
| `doc-writer` | Sonnet | low | doc-storage への記録 |

メインセッションは Opus 5 (1M)。オーケストレータであり、**実装も担当する**。

実装を委譲しないのは、仕様も文脈もメインにあるから。渡し直すと落ちるうえ、
サブエージェントは親のキャッシュを読まないので差し戻しのたびにゼロから始まる。
「書いた本人とは別の文脈が検証する」分離は `test-runner` と `/code-review`
の2つで足りる。`plan-reviewer` には書き込みツールを持たせていない。指摘だけを返す。

## スキル

| スキル | 内容 |
|---|---|
| `/spec <作りたいもの>` | 対話で仕様を詰めて書き出す。実装はしない |
| `/feature <説明>` | 計画 → レビュー → 実装 → 検証 → 記録 |
| `/plan-review` | 直近のプランを `plan-reviewer` に批評させる |
| `/doc [話題]` | doc-storage に記録 |
| `/doc-init` | 現プロジェクトのドキュメント枠を作成 |

検証は組み込みを使う。`/code-review`（差分レビュー）、`/run`（アプリを起動して
変更を確かめる）、`/goal`（完了条件を満たすまで自動でターンを継続する）。

## 推奨の使い方

### 毎セッションの先頭

モデルと effort をここで決めて、**以降は変えない**。
途中で変えると会話全体が再処理される。

- 通常の作業 → `opus` / `high`（既定のまま）
- 重い実装、長時間の自走 → 最初から `opus` / `xhigh`

前のタスクと無関係なら `/clear` から始める。

### タスクの大きさで3つに分岐する

**A. 小さい変更（diff を1文で説明できる）— `/feature` を使わない**

```
> src/auth.ts の login で、セッション期限切れ時に 401 を返すようにして。
  テストも走らせて
```

直接依頼する。プランもサブエージェントも挟まない。ここで `/feature` を
通すのが一番よくある無駄。

**B. 中くらい（複数ファイル、方針に迷いがある）**

```
> /feature Google OAuth のログインを追加する
```

探索 → プラン → `plan-reviewer` の批評 → 実装 → `test-runner` と
`/code-review` を並列 → `/run` で確認 → 記録。

**C. 大きい / 仕様が固まっていない**

```
> 通知機能を作りたい
```

`/spec` が起動して `AskUserQuestion` で詰めてくる。仕様が書けたら
**`/clear` して新しいセッションで `/feature <仕様のパス>`**。
仕様を詰めた文脈を持ち越さず、クリーンな状態で実装に入る。

### 放置して自走させたいとき

```
> /goal test/auth の全テストが通り lint がクリーン。または20ターンで停止
```

別モデルが毎ターン条件を判定し、満たすまで自動でターンを継続する。
席を立てるのはこの形のときだけ。

### 人が手を動かすところ

「何を作るか」は人が決め、「どう作るか」はエージェントに任せる。
介入が要るのは4箇所だけ。

1. セッション先頭のモデルと effort
2. プラン確定時（`Ctrl+G` でプランをエディタで直接編集できる）
3. `plan-reviewer` の指摘の採否。鵜呑みにしない
4. `/goal` の完了条件を書くとき

### 区切りとコミット前

```
> /code-review high        # コミット前は effort を上げる
> /doc 今回の設計判断
> /clear
```

### 成果物の置き場

| | 場所 |
|---|---|
| 仕様 / プラン / レビュー / 調査 / 設計判断 | doc-storage の `<project>/claude-doc/` |
| ビルド・起動の手順 | リポジトリの `.claude/skills/run-<名前>/`（コミットする） |
| コード | リポジトリ |

## 設計方針

Claude 5 系は**手順を細かく規定すると出力品質が落ちる**。
このハーネスの定義は意図的に短い。編集するときも以下を守る。

- 書くのは「役割 / 完了条件 / 使える検証手段」の3点。手順を列挙しない
- **「作業を検証しろ」と書かない**。Opus 5 は指示なしで自己検証する。
  明示すると過剰検証になり時間とトークンを浪費する
- 代わりに検証の道具を用意する。`/run-skill-generator` で手順を記録し、
  `/run` と `/goal` で閉じたループにする。道具があれば自走する
- 組み込みで足りるものは作らない
- スコープ規律と簡潔性は書く（Opus 5 は冗長化・範囲拡大しやすい）
- 実装はメインが持つ。委譲するのは、出力が大量で文脈を埋めるときと、
  別のモデルに見せる価値があるときだけ（Opus 5 は委譲しすぎる）
- 決定的に守らせたいことはフックか `env` でやる。プロンプトで念押ししない
- モデルと effort はセッション先頭で決める。途中変更はキャッシュを全部捨てる
- 環境依存のパスは1箇所に閉じる。散らすとフォークした人が全部追う羽目になる

## ハーネス自体を編集するとき

CLAUDE.md とエージェント定義は**セッション開始時に固定される**。
編集しても現セッションには反映されないので、`/clear` か再起動が必要。
キャッシュが効いているかは `/usage` の `Prompt cache (main)` 行で確認できる。

ファイルを足したら `./install.sh` を再実行する。
消したファイルを指す古いリンクも、そこで一緒に外れる。
