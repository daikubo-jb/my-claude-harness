# my-claude-harness

Claude Code（Anthropic の CLI コーディングエージェント）の、**自分が実際に毎日使っている
設定一式**。汎用フレームワークではなく、1人の作業環境をそのまま置いたもの。
そのままフォークして自分の環境に持っていける形にしてある。

やっていることは Anthropic が公開している使い方をほぼそのままなぞっている。

- 探索 → 計画 → 実装 → 検証 → コミット の順に進める
- 恒久的なルールは `CLAUDE.md` に置いて毎セッション固定する
- 「書いた本人とは別の文脈が検証する」分離を入れる
- **組み込みで足りるものは作らない**

追加しているのはサブエージェント4つとスキル7つ（スラッシュコマンド6つ＋配置規約1つ）、
それに Stop hook が1本だけ。残りは組み込みの `/code-review` `/run` `/goal`
`/run-skill-generator` を使っている。

Claude Code 2.1.269 で動作確認している。

## 考え方

**ユーザーはコマンドを覚えない。** 作りたいものを普通に言えばいい。
完了条件を1文で書けるかを見て、そのまま実装するか、`/feature` に入るか、
`/spec` で詰め直すかは、依頼を聞いた側が決める。
レビューの起動も同じで、条件に当たったら自分から呼ぶ。
人が打つのはモデルの選択と、判断を上書きしたいときだけ。

**分岐を「モデルの判断」ではなく「観測できる事象」で決める。**
「難しそうなら相談する」「自信が無ければ止まる」のような自己申告のトリガーは置かない。
2回失敗した、不変条件のファイルに触った、検証が落ちた — 外から見て分かることだけで分岐する。

**モデルはタスクの途中ではなくセッションごと切り替える。**
設計・仕様は上位モデル（Opus / Fable）、実装・実験・記録は Sonnet。
切替点は `/spec` の末尾（`/model sonnet` → `/clear` → `/feature <パス>`）。
途中で相談相手を足すのではなく、フェーズごとセッションを分ける。

**守らせたいことは文言ではなく機構に置く。** ルールは3種類に分けて置き場所を固定している。

| 種類 | 効き方 | 実装 |
|---|---|---|
| 禁止 | やらせない | `permissions.deny` / PreToolUse hook |
| 検査 | やらせるが結果を見せる | PostToolUse hook（ブロックしない） |
| 完了ゲート | 通るまで「完了」にしない | Stop hook（`hooks/verify-gate.sh`） |

## 構成

```
CLAUDE.md                全プロジェクト共通のルール
agents/                  サブエージェント定義
skills/                  スキル（スラッシュコマンドと、参照用の配置規約）
hooks/verify-gate.sh     完了ゲート（Stop hook）。許可したリポジトリでだけ動く
settings-fragment.json   settings.json へマージする断片（deny と Stop hook）
scripts/verify-harness.sh ハーネス自身の検証
install.sh               ~/.claude へリンクを張り、設定をマージする
```

**このリポジトリがマスター**で、`~/.claude` 側はシンボリックリンク。
ここを編集すれば全プロジェクトに即反映される。

## 導入

置き場所はどこでもよい。以下は `~/p-dev/my-claude-harness` に置いた場合。

```sh
git clone <このリポジトリ> ~/p-dev/my-claude-harness
cd ~/p-dev/my-claude-harness
```

`jq` が要る（`settings.json` のマージに使う）。無ければ `brew install jq`。

### 1. 環境依存の1行を書き換える

このリポジトリで環境に依存するのは、ドキュメントの保管先1つだけ。
`skills/doc-storage/SKILL.md` の中の次の行を自分の環境に合わせる。

```
DOC_STORAGE_ROOT=~/dev/doc-storage
```

他のファイルはこのパスを持たず、`skill: doc-storage` を参照している。
書き換えるのはここだけでよい。ディレクトリ自体は先に作っておく。

### 2. インストール

```sh
./install.sh
```

やることは2つ。

1. `~/.claude/{agents,skills,hooks}` に1ファイルずつリンクを張り、
   `~/.claude/CLAUDE.md` もこのリポジトリを指す
2. `settings-fragment.json` を `~/.claude/settings.json` に `jq` でマージする
   （`permissions.deny` は和集合、`hooks.Stop` は verify-gate のエントリだけ差し替え）

2回流しても結果は変わらない。

> **注意**: `~/.claude` に同名のファイルがあれば `<名前>.bak.<日時>` に退避されたうえで
> リンクに置き換わる。`settings.json` はリンクせず、退避コピーを残したうえで
> 上の2キーだけを足す。**既存のキー・hook・deny は消さない。**

> **リポジトリを移動したら `./install.sh` を再実行する。** リンクは絶対パスなので、
> 移動しただけで全部切れてハーネスが丸ごと無効になる。エラーは出ず、
> ただ効かなくなるだけなので気付きにくい。

### 3. settings.json に手で足す

`install.sh` が触らない分。実行後にそのまま表示されるので、それを貼ればよい。

```json
{
  "permissions": {
    "additionalDirectories": ["/Users/<you>/dev/doc-storage"]
  },
  "env": {
    "CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS": "4",
    "CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH": "2",
    "CLAUDE_CODE_GOAL_CHECKIN_MINUTES": "0"
  }
}
```

`additionalDirectories` は doc-storage への書き込みを許可するため（`~` は展開されない）。
`env` の上2つは委譲の上限（既定は同時20）。プロンプトで念押しせず、ここで決定的に止める。
3つ目は `/goal` がアイドル中に自分からターンを開始してフルコンテキストを送るのを止める。

**`model` は書かない。** `/model` が同じファイルを書き換えるので、リポジトリ側で
固定すると互いに上書きし合う。セッションごとに `/model` で選ぶ。

### 4. プロジェクトごとに1回だけ

```
cd /path/to/your-project
claude
> /run-skill-generator     # ビルド・起動の手順を .claude/skills/run-*/ に記録
> /doc-init                # doc-storage に枠を作る
```

**`/run-skill-generator` が肝。** ビルド・起動の手順が `.claude/skills/run-<名前>/`
に記録され、以降 `/run` と全エージェントがそれに従う。これが無いとエージェントが
自走できない。

そのうえでリポジトリ側に2つ置く。**どちらも無いと、ハーネスの分岐が2つとも発火しない。**

#### `CLAUDE.md` に「不変条件」節

`/feature` が `plan-reviewer` を呼ぶ**唯一のトリガー**。
壊れると気付きにくく、壊れたときのコストが高いファイルだけを3〜5個挙げる。
多く挙げるほど毎回 Fable が走って高くつくので、絞る。

```markdown
## 不変条件

これらに触る変更は、実装前に plan-reviewer に見せる。

- `src/pipeline/encoder.cpp` — 出力フォーマットが下流に固定で刺さっている
- `configs/model.yaml` — 変えると既存のチェックポイントが読めなくなる
```

#### `.claude/verify-fast.sh` と許可リスト

完了ゲートの中身。実行ビットを立ててコミットする。
**あわせて `~/.claude/verify-gate-allow` にこのリポジトリのパスを1行足す。**
足さない限り実行されない（他人のリポジトリのスクリプトを走らせないための歯止め）。

```sh
echo "$PWD" >> ~/.claude/verify-gate-allow
```

```bash
#!/usr/bin/env bash
set -euo pipefail
npm run lint
npm run typecheck
npm test -- --changed
```

判断基準は1つだけ。**「質問に答えただけのターンでも毎回走って許せる長さか」。**
Stop hook はターンごとに起動する。長い eval や実機の soak はここに入れず、
`/feature` の手順の中で明示的に回す。

置いたら効いているか確かめる。末尾に `exit 1` を一時的に足して適当な質問を1つ投げ、
1回差し戻されて止まればいい。確認したら戻す。

ドキュメントをリポジトリ内で管理するプロジェクトなら `/doc-init` は不要。
ドキュメント機能自体が要らないなら、`doc-writer` / `/doc` / `/doc-init` を消して
`CLAUDE.md` のドキュメント節を削れば、残りはそのまま動く。

## サブエージェント

| エージェント | モデル | effort | 起動条件 |
|---|---|---|---|
| `plan-reviewer` | Fable | xhigh | 不変条件のファイルに触る / 1回が高い実験の前 |
| `advisor` | Opus | high | 同じ完了条件に**異なる手で2回**失敗した |
| `test-runner` | Sonnet | medium | 完了条件が通った後の検証 |
| `doc-writer` | Haiku | low | 記録 |

メインセッションは Sonnet 5。オーケストレータであり、**実装も担当する**。
設計・仕様を詰めるセッションだけ Opus / Fable にする。

実装を委譲しないのは、仕様も文脈もメインにあるから。渡し直すと落ちるうえ、
サブエージェントは親のキャッシュを読まないので差し戻しのたびにゼロから始まる。
「書いた本人とは別の文脈が検証する」分離は `test-runner` と `/code-review`
の2つで足りる。`plan-reviewer` と `advisor` には書き込みツールを持たせていない。

`advisor` に聞くのは「どう直すか」ではなく「**どの前提が間違っているか**」。
実装案をもらうためではないので、2回失敗するまでは呼ばない。

## スキル

**ほとんどは打たなくていい。** 依頼を聞いた側が、完了条件を1文で書けるかどうかで
どれに入るかを判断して自分から起動する。打つのは、明示的にその手順に入れたいときだけ。

| スキル | 内容 | 起動 |
|---|---|---|
| `/spec <作りたいもの>` | 対話で仕様を詰めて書き出す。実装はしない（上位モデルで） | 自動 / 手動 |
| `/feature <説明>` | 計画 → 実装 → 検証 → 記録（Sonnet で） | 自動 / 手動 |
| `/plan-review` | 直近のプランを `plan-reviewer` に批評させる | 自動 / 手動 |
| `/doc [話題]` | doc-storage に記録 | 手動のみ |
| `/doc-init` | 現プロジェクトのドキュメント枠を作成 | 手動のみ |
| `/harness-review` | worklog からハーネスの改善を提案させる | 手動のみ |

「手動のみ」の3つは frontmatter に `disable-model-invocation: true` を置いてある。
`/doc-init` は1回きりの初期化、`/harness-review` はハーネス自身を書き換えるので、
どちらも人が起動点を握る。`/doc` は `/feature` の中から `doc-writer` を直接呼ぶので、
自動起動の経路は別にある。

検証は組み込みを使う。`/code-review`（差分レビュー）、`/run`（アプリを起動して
変更を確かめる）、`/goal`（完了条件を満たすまで自動でターンを継続する）。

## ガードレール

### 禁止（`permissions.deny`）

プロジェクトによらないものだけを6件。`install.sh` がマージする。

| ルール | 止めるもの |
|---|---|
| `Bash(git push*--force*)` | 履歴の破壊。`--force-with-lease` も含めて止める |
| `Bash(git push -f *)` / `Bash(git push * -f)` | 同上の短縮形 |
| `Bash(rm -rf /*)` | 絶対パスの `rm -rf`（ルート直下だけを指す書き方が無いので広めに取る） |
| `Bash(rm -rf ~*)` | ホーム以下の `rm -rf` |
| `Edit(<DOC_STORAGE_ROOT>/*/human-doc/**)` | 人間が書いた文書の書き換え |

Bash のルールは**コマンド文字列にしか当たらない**ので、オプションの位置を変えた書き方を
1つのルールで網羅できない。`git push` を3行に分けているのはそのため。

`<DOC_STORAGE_ROOT>` は `install.sh` が `skills/doc-storage/SKILL.md` の1行から読んで
置換する（このリポジトリは public なので個人のパスをコミットしない）。

### 完了ゲート（`hooks/verify-gate.sh`）

Stop hook を1本だけ登録する。契約は次のとおり。

- **`~/.claude/verify-gate-allow` に書いたディレクトリ（とその配下）でだけ動く。**
  リストに無ければ何もしない。`install.sh` が空の雛形を作るので、
  使うリポジトリを1行ずつ足す。既定では1つも動かない
- そのうえで `.claude/verify-fast.sh` が実行可能な形で**あれば実行する。
  無ければ何もしない**
- 落ちたら exit 2 で、実際の出力とともにセッションを差し戻す
- 差し戻しは**1回だけ**（`stop_hook_active`）。同じ失敗で回り続けさせない
- タイムアウト 300 秒

`verify-fast.sh` には**数分で終わる検証だけ**を置く。これはターンの終わりごとに走る。
重い検証（長い eval、実機の soak）はここに入れず、`/feature` の手順の中で明示的に回す。

許可リストを挟んでいるのは、**Stop hook が `permissions` を通らない**ため。
これが無いと、clone してきただけのリポジトリにコミットされたスクリプトが、
セッションを1ターン回すだけで実行されてしまう。

### 限界

hooks と deny は Claude が書くコマンド文字列と組み込みのファイルツールを見る。
`sed -i`、`/bin/rm`、`sh -c '...'`、`git -C . push --force`、スクリプト経由の書き込みは通る。
本当に不可逆なもの（main への force push）はリモート側のブランチ保護で守ること。
**ハーネスは最後の砦ではなく、その手前の網。**

## 自己改善ループ

データ収集は毎回自動、変更の提案は定期に人が起動、適用は人が承認。
ハーネスに自分を書き換えさせない。

1. **収集** — `/feature` の記録ステップで、worklog に「ハーネスへの示唆」欄を固定で置く。
   書くのは3つだけ。効かなかった指示 / hook が止めた回数と内容 /
   `advisor`・`plan-reviewer` の指摘の採否。計測基盤は作らない
2. **提案** — `/harness-review`（月1か10セッションごとに手で起動）。全プロジェクトの
   worklog を横断し、**昇格**（2回以上破られた文言 → hook か deny）/
   **削除**（効いた記録が無いルール）/ **追加**（繰り返した事故 → 検査 hook か `run-*`）
   の3分類で出す
3. **適用** — 採用するものを人が選ぶ。`bash scripts/verify-harness.sh` を通してから人がコミットする

歯止めが1つ。**削除の提案がゼロのレビューは疑う。** ルールは放っておくと増える一方になる。

作業中のセッションではハーネスを書き換えない。気付いたことは示唆欄に書くだけにする。

### harness-review の回し方

**このリポジトリで**起動する。実際に編集するのがここだから。モデルは `sonnet` でいい
（材料は worklog に書き出されていて、読み解く必要が無い）。

```sh
cd ~/p-dev/my-claude-harness && claude
> /harness-review
```

回すタイミングは、暦よりも**示唆欄が3〜4件溜まったとき**。
どのプロジェクトにも `verify-fast.sh` が無いうちは早い。
「hook が止めた回数」が常にゼロで、示唆欄の3項目のうち1つが埋まらないまま溜まる。

判断するのは2点だけ。

1. **削除の提案がゼロなら疑う。** ゼロで出してきたら「なぜ削れるものが無いのか」を説明させる
2. **文言を足す提案は、hook にも deny にもできない理由が言えるときだけ通す。** 文言は最後の手段

採用は1件ずつ選ぶ。全採用しない。
そのあと `bash scripts/verify-harness.sh` を通してから自分でコミットする。
ファイルが増減していたら `./install.sh` を再実行。変更は `/clear` するまで効かない。

## 推奨の使い方

### 毎セッションの先頭

モデルと effort をここで決めて、**以降は変えない**。
途中で変えると会話全体が再処理される。

- 実装・検証・記録 → `sonnet`
- 設計・仕様・研究結果の解釈 → `opus` か `fable`

前のタスクと無関係なら `/clear` から始める。

### 頼み方

**普通に頼む。** どの手順に入るかは、依頼を聞いた側が判断する。
判定は1つだけ — **完了条件を「検証可能な1文」で書けるか**。

```
> src/auth.ts の login で、セッション期限切れ時に 401 を返すようにして
```
→ 書けて、diff も1文。**そのまま実装する。** プランもサブエージェントも挟まない。

```
> Google OAuth のログインを追加して
```
→ 書けるが、触るファイルが複数で方針が1本に決まらない。**`/feature` に入る。**
完了条件を1文で提示して合意を取ってから、探索 → 実装 ⇄ 検証 → `test-runner` → 記録。

```
> 通知機能を作りたい
```
→ 書けない。**`/spec` に入り**、`AskUserQuestion` で詰めてくる。
仕様が書けたら **`/model sonnet` → `/clear` → `/feature <仕様のパス>`** を案内される。
仕様を詰めた文脈を持ち越さず、安いモデルのクリーンなセッションで実装に入る。

途中のレビューも同じで、**条件に当たったら自分から呼ぶ。**
不変条件のファイルに触れば `plan-reviewer`、異なる手で2回失敗すれば `advisor`、
コミット前には `/code-review`。条件は `CLAUDE.md` の表に1箇所だけ書いてある。

打つ必要があるのは、判断を上書きしたいときだけ。
「`/feature` を通さず直接やって」「これは `/spec` から」のように言えばいい。

なお `/spec` は上位モデルで回したいので、`/model opus` だけは先に打つ。
これはモデル側から変えられない。

### 放置して自走させたいとき

```
> /goal test/auth の全テストが通り lint がクリーン。または20ターンで停止
```

別モデルが毎ターン条件を判定し、満たすまで自動でターンを継続する。
席を立てるのはこの形のときだけ。

止まるのは3つ。異なる手で2回失敗して `advisor` でも解けないとき、
人の判断が要るとき、実機の事実が要るとき。

### 人が手を動かすところ

「何を作るか」は人が決め、「どう作るか」と「どの手順で作るか」はエージェントに任せる。
介入が要るのは5箇所だけ。**どれもコマンドを覚える話ではない。**

1. セッション先頭のモデル選択（設計か実装か）。ここだけはモデル側から変えられない
2. 提示された完了条件に合意するとき。違うと思ったら直す
3. `plan-reviewer` / `advisor` の指摘の採否。鵜呑みにしない
4. `/goal` で放置に入るとき
5. `/harness-review` の提案の採否

2 が実質の主戦場。**完了条件が間違っていれば、その先は全部正しく間違う。**

### 区切りとコミット前

```
> /code-review high        # コミット前は effort を上げる
> /doc 今回の設計判断
> /clear
```

### 成果物の置き場

| | 場所 |
|---|---|
| 仕様 / プラン / レビュー / 調査 / 作業記録 / 設計判断 | doc-storage の `<project>/claude-doc/` |
| ビルド・起動の手順 | リポジトリの `.claude/skills/run-<名前>/`（コミットする） |
| 数分で終わる検証 | リポジトリの `.claude/verify-fast.sh`（コミットする） |
| コード | リポジトリ |

## 設計方針

Claude 5 系は**手順を細かく規定すると出力品質が落ちる**。
このハーネスの定義は意図的に短い。編集するときも以下を守る。

- 書くのは「役割 / 完了条件 / 使える検証手段」の3点。手順を列挙しない
- **「作業を検証しろ」と書かない**。指示なしで自己検証する。
  明示すると過剰検証になり時間とトークンを浪費する
- 代わりに検証の道具を用意する。`/run-skill-generator` で手順を記録し、
  `/run` と `/goal` と `verify-fast.sh` で閉じたループにする
- 組み込みで足りるものは作らない
- 分岐の条件は観測できる事象で書く。モデルの自己申告をトリガーにしない
- 決定的に守らせたいことは hook か `permissions.deny` か `env` でやる。
  プロンプトで念押ししない
- 同じルールを複数のファイルに重複させない。書くなら1箇所
- モデルと effort はセッション先頭で決める。途中変更はキャッシュを全部捨てる
- 環境依存のパスは1箇所に閉じる。散らすとフォークした人が全部追う羽目になる

## ハーネス自体を編集するとき

編集は `/harness-review` からだけ行う。作業中のセッションで書き足さない。
「忘れないように」で足し続けると、CLAUDE.md は放っておくと数十 KB になる。

CLAUDE.md とエージェント定義は**セッション開始時に固定される**。
編集しても現セッションには反映されないので、`/clear` か再起動が必要。
キャッシュが効いているかは `/usage` の `Prompt cache (main)` 行で確認できる。

変更したら検証を通す。

```sh
bash scripts/verify-harness.sh
```

隔離した `HOME` で `install.sh` を2回流し、リンク・設定マージ・冪等性・
Stop hook の挙動まで実際に確かめる。

ファイルを足したら `./install.sh` を再実行する。
消したファイルを指す古いリンクも、そこで一緒に外れる。

## 既知の制約

- **Cowork では効かない。** `~/.claude/CLAUDE.md` がシンボリックリンクだと読み飛ばされる
- deny と hook は最後の砦ではない（上の「限界」）
