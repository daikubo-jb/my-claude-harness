$ARGUMENTS

このセッションは `sonnet` で回す想定。設計から詰め直すなら上位モデルの `skill: spec` へ戻る。

まず完了条件を「検証可能な1文」で書けるか試す。

- 書けて、diff も1文で説明できる規模 → 以下を飛ばして直接実装する
- 書けない、かつ規模が大きい → `skill: spec` で仕様を固めてから出直す

書けたら以下を進める。

1. **完了条件を確定する。** 検証方法は `.claude/skills/run-*/` かプロジェクトの
   CLAUDE.md から取る。無ければ `/run-skill-generator` で先に記録させる
2. **探索する。** 読む範囲が広いなら `Explore` に投げる
3. **リスクゲート。** 次のどちらかに当たるときだけ `plan-reviewer` に批評させる
   - プロジェクトの CLAUDE.md が「不変条件」として挙げたファイルに触る
   - 1回の試行が高い（実機・数十分かかる）。自律に入れず、事前に見せる

   どちらでもなければ省略する。プランを立てただけでは呼ばない
4. **自律開始。** 完了条件を提示し、放置して自走させるならユーザーに
   `/goal <完了条件>` を打ってもらう
5. **実装 ⇄ 検証。** 自分で書く。サブエージェントには投げない
   - 同じ完了条件に**異なる手で2回**失敗した → `advisor` に
     「どの前提が間違っているか」を問う。同じ修正のリトライは1回に数える。
     渡すもの: 目的と完了条件 / 2つの試みそれぞれの内容と実際の失敗出力 / 除外できたこと
   - `advisor` の後も解消しない → 停止して人に返す
   - 人の判断・実機の事実が必要になった → 到達点を記録して停止
6. **完了条件が通ったら検証を回す。** `test-runner` と `/code-review` を1メッセージ内で
   同時に起動する。プロジェクト側に `<domain>-reviewer` があれば一緒に。
   アプリの挙動が変わるなら `/run` で実際に動かして確かめる
7. **指摘 → 修正 → 影響する検証だけ再実行。** 全部は回し直さない
8. **記録する。** 長時間・高リスク・引き継ぎのいずれかなら `doc-writer` に渡す。
   「何を・なぜ・どう変えたか」の要約と、**「ハーネスへの示唆」**を添える

サブエージェントにはこの会話が見えない。
仕事に必要な文脈はプロンプトに含めて渡す。

作業中にハーネス（`~/.claude`）を書き換えない。
気付いたことは「ハーネスへの示唆」に書くだけにして、変更は `skill: harness-review` で行う。
